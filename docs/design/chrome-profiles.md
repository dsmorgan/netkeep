# Chrome profiles: research and mechanics

This document holds the evidence and the mechanics behind [ADR 0012](../adr/0012-chrome-profiles.md). The ADR holds the decision: one netkeep Chrome, on the dedicated profile with the debugging port, holds the UI, LinkedIn, and setup steps such as Gmail linkage. Researched 2026-10-17 for #595, and revised the same day after the maintainer's review.

## How netkeep attaches today

- `linkedin.cdp_url` (default `http://127.0.0.1:9222`) names the port. `AttachProvider` in `netkeep/linkedin/browser.py` connects with Playwright's `connect_over_cdp` and reuses `browser.contexts[0]`. It never creates a context, and it never closes the browser or the context. It logs a warning when the attached Chrome has more than one context.
- The profile is `<data dir>/chrome-profile` (`CHROME_PROFILE_DIRNAME`). `netkeep browser launch` and `GET /linkedin/browser` print the command from `chrome_launch_command` in `netkeep/services/browser_launch.py`: `--remote-debugging-port=<port>`, `--no-first-run`, `--no-default-browser-check` and `--user-data-dir=<profile>`, and nothing else. `scripts/chrome.sh` (`make chrome`) runs that command for a person.
- Every attach checks that the Chrome on the port is the dedicated profile (#624), before it reads a context or opens a tab. On the attach's own connection it sends one `SystemInfo.getProcessInfo` and takes the pid of the `browser` process. It then reads the profile's `SingletonLock`, a symlink to `<hostname>-<pid>` that Chrome writes for the browser process holding that `--user-data-dir`. The two pids must match. Another pid, no lock, an unreadable lock, or a Chrome that names no browser process all refuse the attach (`ProfileRefused`, a `BrowserUnavailable`; the run's stop reason is `profile_refused`, not `browser_unavailable`), and preflight and `posture --probe` show the refusal in the "dedicated chrome profile" row. Nothing falls back to attaching. The pure decision is `check_dedicated_profile` in `netkeep/chrome_profile.py`, which imports nothing from `linkedin/`, so #636's launcher can call it too.
- Why that pair: `Browser.getBrowserCommandLine` answers only when Chrome runs with `--enable-automation`, which netkeep's Chrome never does. `/json/version` and `Browser.getVersion` name no profile, and Chrome didn't write `DevToolsActivePort` into the profile for a fixed port. `chrome://version` names the profile path but needs a tab. Checked on Chrome 155, headless, with a scratch profile on an unused port.

## Why not your everyday Chrome

Chrome 136 (2025) and later ignore `--remote-debugging-port` and `--remote-debugging-pipe` when Chrome runs on the default user data directory. The flags work only with a non-default `--user-data-dir`, which uses its own encryption key. Chrome made this change because attackers used remote debugging to steal cookies after App-Bound Encryption shipped. Source: [Changes to remote debugging switches to improve security](https://developer.chrome.com/blog/remote-debugging-port).

Chrome 144 added an opt-in at `chrome://inspect/#remote-debugging` that lets a tool connect to your running browser. Chrome asks you to accept each session and shows a "controlled by automated test software" banner while one is active. Sources: [Let your coding agent debug your browser session](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session) and [Auto-connect](https://developer.chrome.com/docs/devtools/agents/use-cases/auto-connect). netkeep can't run unattended that way, and #624 refuses such a Chrome.

A second profile inside your everyday Chrome's data directory (`--profile-directory`) is still on the default user data directory, so it doesn't work either. So "the same profile" in ADR 0012 means netkeep's dedicated profile. It's a second Chrome window with its own icon in the window list, and it is the one place you look when you operate netkeep.

## How Gmail linkage works today

- **Google Cloud setup.** The Settings page's Gmail setup wizard (`frontend/src/features/settings/gmail-setup-wizard.tsx`) links to Google Cloud Console pages (new project, Gmail API, Branding, Audience, Create OAuth client). Each link opens a new tab (`target="_blank"`).
- **Authorization, from the UI.** `POST /mailboxes/oauth/start` (`netkeep/web/api/mailboxes.py`) returns Google's authorization URL, built by `gmail_oauth.begin` with PKCE and a loopback redirect to the API's own `/mailboxes/oauth/callback`. The UI then sends its own tab to that URL (`navigation.assign` in `frontend/src/features/mailboxes/api.ts`). After you allow access, Google redirects that tab to the callback, which exchanges the code and redirects back to the Settings page.
- **Authorization, from the CLI.** The CLI starts its own loopback listener and prints the URL for you to open (`_present_authorization_url` in `netkeep/cli.py`). It never opens a browser.

So the launcher never needs Google's consent URL. In netkeep's Chrome, the wizard's Console tabs and the consent page open in the same Chrome as the UI, and the Google sign-in you make there stays in that profile.

## What runs do with tabs, and what changes

| Path | Today | With the UI in the same Chrome |
| --- | --- | --- |
| Open | `_open_tab` sends `Target.createTarget` with `url: about:blank`, `newWindow: true` and `background: true` (#195, #632), so the run's tab opens in a window of its own and Chrome activates no window. When the run closes its tab, Chrome closes that window if the tab was its last; netkeep never closes a window. On failure, and for a reopen after `bring_tab_forward`, it opens a tab in front with `context.new_page()` in a window Chrome picks, and the failure path logs an "opened in front" note. | Done by #632. Not verified live: where Chrome places the window, and that it takes no focus. |
| Wait for the new tab | `_open_tab` opens a page-level session (`Target.getTargetInfo`) only on a new page whose URL is still `about:blank`, and claims it only by target id (#634). A UI or Google tab you open during the wait gets no session. A tab you open that is still on `about:blank` at that moment can get the read-only read; it's never claimed. | Done by #634. |
| Bring forward | `bring_tab_forward` calls `bring_to_front` once, on the run's own page, before the Message click (ADR 0007, ADR 0008). | Unchanged. With #632, it raises the run's window, not the UI's. |
| Close | The run closes only its own page, except a prefill's handed-over tab. Auto-send closes the sent bubble inside the run's own tab (#516, `_close_by_rule`). | Unchanged. |
| Read other tabs | `bubble_check` (`message-check --bubble`, #495) lists `context.pages` and reads only the tabs on the LinkedIn origin it's given, never the run's own. `tests/test_browser_safety.py` pins every `pages` and `contexts` read in the package, and every `close` and `bring_to_front`, to the run's own tab or LinkedIn's origin (#634). | Done by #634. |
| Network | The body tap (`_open_body_tap`), the package's only `Network.enable`, is a page-level session on the run's own tab. | Unchanged. The UI's traffic isn't seen. |
| Cookies | `_read_session_cookies` in `netkeep/linkedin/preflight.py` calls `context.cookies()` with no URLs, then keeps LinkedIn's two session cookies by name and domain. It copies names and expiry times only. | After Gmail linkage, the jar holds your Google cookies too. **New (#633):** pass LinkedIn's URLs so the read never returns another site's cookies. |

The user's own clicks or typing in a run's tab can still disturb that run. ADR 0012 accepts that near-term. The Phase 7 end state, a bundled or custom browser that controls focus, hides run tabs, and blocks navigation during a run, is #631.

## What a remote-debugging port exposes

The first two bullets describe Chrome's known behavior. Neither has an official source, and neither was verified live for #595. A Chromium issue confirms that two instances can't share one user data directory.

- **One process per profile directory.** Chrome allows one browser process per `--user-data-dir`, guarded by the profile's singleton lock (the `SingletonLock`, `SingletonCookie` and `SingletonSocket` files that `scripts/chrome.sh` clears after a crash). Profiles inside that directory run in the same process. A second launch with the same directory hands its arguments to the running process and exits.
- **The port is browser-wide.** `/json/list`, `Target.getTargets` and `Target.setDiscoverTargets` report every page, worker, and extension target in the process. A client can attach to any of them and call `Runtime.evaluate`, read cookies (`Network.getAllCookies`, `Storage.getCookies`), take screenshots, and navigate.
- **There's no authentication.** Chrome binds the port to loopback and checks the `Host` header and WebSocket origins (`--remote-allow-origins`), but a native program on the same machine passes those checks.
- **What the UI adds.** A client on the port can read the UI's page, and after Gmail linkage, your Google cookies. That client can already drive LinkedIn and read LinkedIn's cookies, which is the asset netkeep protects most. The API itself has no login today: `csrf_violation` (`netkeep/web/security.py`) lets through a request with `X-Netkeep-Client: 1` and no `Origin` or `Sec-Fetch-Site`, so a local program can already press any UI button without the port.
- **A per-install API secret (#618).** If #618 adds one, the UI's page holds it, so a client on the port could read it with `Runtime.evaluate`. That's acceptable for the same reason: a client on the port already controls LinkedIn. The secret still stops local programs that don't have the port.

## Profile and capture pollution (#520)

During the CP8c capture (the setup notes in #520), a netkeep UI tab (`localhost:8000`) was open in the test-account capture profile, not in netkeep's LinkedIn Chrome. It kept polling the API; the top bar alone refetches `/poll-status` every minute, and the UI holds an event stream open. The capture's netlog records the whole browser's traffic, so the UI's requests mixed in with LinkedIn's.

With the UI in netkeep's Chrome:

- **The UI's contact links open LinkedIn here.** A click on a contact's `linkedin.com/in/...` link in the UI opens it in netkeep's Chrome: the right identity, but your own browsing, outside netkeep's budgets. Before, it opened in your everyday Chrome.
- **The UI never talks to LinkedIn.** Its requests go to localhost. LinkedIn's pages can't read the UI's origin, its storage, or the profile's history.
- **Runs don't see the UI's traffic,** because every network session is on the run's own tab.
- **The residual risk is a whole-browser capture,** such as a netlog or `chrome://net-export`, taken in netkeep's Chrome. Close the UI and quit `serve` first, as #520's setup already says.
- **The profile now holds more:** the UI's origin data, and your Google sign-in after Gmail linkage. #633 keeps netkeep's own reads to LinkedIn's cookies.

## The launcher (#636, for #549 and #599)

One function builds one argument list from config and spawns it:

- **Binary.** Run Chrome's binary directly, as an argument list with no shell. On macOS that's `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`; on Linux, `google-chrome`. Don't go through the printed `open -na "Google Chrome" --args ...`: `-n` does start a new process that receives the arguments, but the launcher needs that process's own exit status and no LaunchServices step in between.
- **Arguments.** `--remote-debugging-port=<port>`, `--no-first-run`, `--no-default-browser-check` (which skip Chrome's first-run dialog, #733) and `--user-data-dir=<profile>`, the same tokens `chrome_launch_command` prints, then `--app=<the UI's URL>`, then, from the first-run button only, LinkedIn's sign-in or feed URL as a positional argument. Never a headless flag, never a fresh profile, never another flag or URL. A test compares parsed arguments, not the printed shell lines with their trailing backslashes: the list equals the printed tokens plus these two additions, and checks that only the first-run caller passes the LinkedIn URL.
- **Already running.** When netkeep's Chrome is up with the UI's window open, the launcher brings that window to the front instead (#678). Otherwise the same command hands its arguments to the running process through the profile's singleton, which opens the UI's app window and exits. So `netkeep open` works whether or not that Chrome is running. Not verified live: that the running process honors `--app` and the positional URL on a handoff, and what status the launched process exits with after a headed hand-off on macOS (a headless instance answers any second launch with 21, profile in use, so it can't stand in).

  **Live check for the maintainer.** With netkeep's Chrome running (`make chrome`), close netkeep's UI window in it first: with that window open, `netkeep open` brings it to the front and reports `shown` instead of handing off (#678). Then run `NETKEEP_DATA=<your data dir> netkeep open`. Note its exit status, the status it reports (`handed_off` or `handoff_unconfirmed`, with the launched process's exit status in the message), and whether the UI's app window opened in that Chrome. Run it once more with that window open, and check that it reports `shown`, opens no second window, and brings the window forward. If a headed hand-off always exits with one nonzero code, the launcher can accept that exact code as `handed_off`, still after the `SingletonLock` re-check.
- **Checks before a spawn.** Refuse, and report which case applied, as `scripts/chrome.sh --status` does, when:
  - the port answers but isn't the dedicated profile (#624's check, `check_dedicated_profile`), or
  - a live process holds the profile's singleton lock but the port doesn't answer (a Chrome on that profile without the port; a handoff would open the UI where runs can't attach).
- **Runs.** Starting Chrome cold is refused while a process holds the account's browser lock (checked through `services.runs`), and #599's button is disabled then, as far as the UI knows. Opening the UI's window into a running Chrome is allowed during a run, because it's your act and touches no run tab.
- **Detached.** Run it detached, so the Chrome outlives `serve`.

### As built (#636)

- `netkeep/chrome_spawn.py`: `chrome_argv` builds the list, and `spawn_chrome` runs it with `subprocess.Popen`, no shell, in its own session, with every stream on `/dev/null`. `ChromeLauncher.start` makes the checks first. On Linux, `google-chrome` is found on your `PATH`.
- **The `--app` link** must be exactly `http://127.0.0.1:<serve's port>/...` or `http://localhost:<serve's port>/...`: no userinfo, backslash, whitespace or non-ASCII, and rebuilding it from its parsed parts must give the same string. Python and Chrome parse URLs differently (Chrome reads `\` as `/`), so `http://evil.com\@127.0.0.1:8000/` is refused. A `linkedin.cdp_url` with no valid port refuses too, instead of falling back to 9222.
- **The dedicated check.** With no run attached, the probe holds the local account's activity lock and reads the browser's pid (giving up after 5 s). It does that without Playwright (#675). `CdpIdentityReader` needs the address to name its port, resolves its host once, and uses that one address for both steps. It GETs `/json/version` (one request, one 5 s deadline for the whole answer, at most 64 KiB, only a `200` with a `Content-Length`) for the browser target's websocket. That websocket must be on the same address, at `/devtools/browser/`. It opens the websocket, refusing any redirect on the handshake, sends one `SystemInfo.getProcessInfo`, and closes it. `tests/test_browser_safety.py` pins everything the two transport functions may reach on the stream and the websocket. Playwright's `connect_over_cdp` sets up a browser context as it attaches (`Browser.setDownloadBehavior`), and Chrome with no windows open refuses that ("Browser context management is not supported", checked on Chrome 155): on macOS, closing netkeep's last window leaves Chrome running like that, and the probe used to refuse its own Chrome as `not_dedicated`. The pid must still be the live one in the profile's `SingletonLock`. A run's attach still goes through `connect_over_cdp` and reads the pid on that same connection; on a Chrome with no windows it ends `browser_unavailable`, and its message says to reopen the window with `netkeep open`. While a run holds the lock, a second CDP client would drop the run's connection, so the probe connects to nothing. Instead, every attach writes the Chrome pid its #624 check verified into its lock file's holder note (`browser_pid`), and a hand-off needs that pid to be the live process in the profile's `SingletonLock`. A run that holds the lock but hasn't attached yet has no pid there, so the launcher refuses. Chrome doesn't write `DevToolsActivePort` for a fixed `--remote-debugging-port` (checked on Chrome 155), so that file isn't evidence.
- **Runs.** A cold start reads every `browser-*.lock` under `<data dir>/locks` (`services.runs.any_browser_lock_held`), so it needs no database.
- **Exit status, then the lock.** The launcher watches the process for up to 5 seconds, then reads `SingletonLock` again. A hand-off is `handed_off` when the process exited 0 and the verified pid still holds the profile. It's `failed` when the process exited 21 (`RESULT_CODE_PROFILE_IN_USE`: Chrome refused the hand-off and aborted, which a test against a running headless instance showed reaches nothing) or was killed by a signal; `netkeep open` then exits 1. It's `handoff_unconfirmed` when the process exited with any other positive status and the verified pid still holds the profile: Chrome may exit nonzero after notifying the running instance, so the window probably opened, and `netkeep open` says so, exits 0, and still prints the link. A cold start is `started` only while the process runs and no other pid holds the profile. Anything else (a changed pid, or a launched process still running) is `failed` and names both pids. Not verified live: Chrome's POSIX singleton kills a running Chrome that doesn't acknowledge within about 20 s and takes over its profile. A hand-off to a hung netkeep Chrome could therefore replace it, and the re-check reports that as a failure, not a start.
- **An open window first (#678).** Before a hand-off, the launcher asks the probe to bring an open UI window to the front, so **Start Chrome**, `netkeep open` and the start at startup don't add a window each time. On the identity read's one websocket, under the same lock, and only after the pid passes #624's check, it sends `Target.getTargets` (no params). The first target whose `type` is `page` and whose URL is `http` on exactly `127.0.0.1:<serve's port>` or `localhost:<serve's port>` (no userinfo, no other port, no `https`, no worker or frame; `ui_window_target`) gets one `Target.activateTarget` with its `targetId`. When Chrome answers that with a result, the launch is `shown`: nothing is spawned, and the pid is the verified one. With no such page, an error, an answer that isn't a result, or no answer within its own 2 s step (`FRONT_STEP_TIMEOUT_S`, on top of the probe's 5 s), it hands off as before; a failure there never loses the pid. A run's tab is on LinkedIn, so it never matches. The launcher asks for no front on the first-run path, whose hand-off also opens LinkedIn's sign-in page, and while any browser lock is held (`any_browser_lock_held`, read before the probe takes its own lock): a held lock means a run is attached or about to be, and runs never take focus (#645). Just before `Target.getTargets`, the read looks at every browser lock again, skipping the probe's own (`any_browser_lock_held(ignoring=...)`), so a run of another account that attached after the first look still gets no front. A held account lock also makes the probe connect to nothing, as before. An answer counts only when its `id` is that exact int (JSON's `true` or `1.0` isn't id 1), and a close that runs out of time after every answer arrived keeps those answers, so a window already brought forward is reported as `shown`. `tests/test_browser_safety.py` allows the two methods only at `_read_process_info`, with these params, and the whole-function pin (`tests/identity_read_transport.txt`) holds that function and `ui_window_target`. Not verified live: that `Target.activateTarget` on an `--app` window raises that window over other apps on macOS, as it does over Chrome's own windows.
- **IPv6.** `serve --host ::1` isn't supported for launch: its base is `http://[::1]:<port>`, which the `--app` check refuses, so the launch reports `failed`. Use `127.0.0.1` or `localhost`.
- **Callers.** `netkeep open` (it still prints a one-time link, for another browser, and `--link-only` prints only that). `serve` puts the launcher on `app.state.chrome_launcher` as a `services.chrome_launch.ChromeSpawner`. `POST /api/v1/linkedin/browser/start` (owner only) submits it to the task runner, answers `202`, and publishes `browser.launch` with the result. `{"first_run": true}` adds LinkedIn's sign-in page. #549's open-at-login isn't built yet.

### As built (#599)

- **One submit.** `services.chrome_launch.submit_launch` is the one way to run the launcher from `serve`: one task named `chrome_launch` at a time, whose result is published as `browser.launch`. It has two callers. The **Start Chrome** route (`start_browser`) answers `409` while any launch is under way. `serve`'s start at startup (`worker.start_chrome_at_startup`) is the other. So a press while the startup launch is settling gets a 409, and nothing launches twice. `tests/test_browser_safety.py` pins every reach of `submit_launch`, `app.state.chrome_launcher`, the startup entry points (`start_chrome_at_startup`, `_after_listening`, `app.state.after_listening`), the two factories and `ChromeLauncher` to these callers, the health route's check, the lifespan and `netkeep open`. It pins every `.start` in the files that hold a launcher, and it pins that a `ChromeLauncher` is built only as the value of each factory's `return` and is held only on `app.state.chrome_launcher` or started at once. #660 closed the two limits #664 documented. A launcher an allowed function reads may only be checked against `None`, handed to `submit_launch`, or returned by the route's `_launcher` helper, so it can't be stored under another name or passed on. A read by a computed name (`getattr` with a built string, `vars()`, `__dict__`, `State._state`) is a finding anywhere in the package unless it is on the scanner's reviewed list. What it still can't see: an attribute written through a computed name (`setattr`), which reaches no launcher by itself.
- **Start at startup.** With `linkedin.start_chrome_at_startup` on (off by default), the lifespan runs `app.state.after_listening` as a task. It waits for uvicorn's `started` (`serve` sets `app.state.listening`), reads the setting for the local owner, and submits one launch, never `first_run`. When a live process already holds the profile's `SingletonLock`, it still submits the launch (#679): the launcher's identity read checks that the Chrome on the port is netkeep's, then brings its open UI window to the front, or hands off when none is open (#678), so the UI is visible after every start. As defense in depth against a `serve` that crashes after listening and is restarted by launchd, it records the pid and time of each startup launch whose outcome is `handed_off` or `shown` in `<data>/chrome-startup-handoff.json` (a refused, unconfirmed or failed one records nothing, so the next restart tries again), and skips, with a log line, a second one to the same live pid within 5 minutes. #678 keeps that cooldown: a front step that fails falls back to a hand-off, which adds a window, and a front on every restart would keep taking focus from what you're doing. So a **Restart netkeep** press within 5 minutes of the last one shows nothing; **Start Chrome** still does. It starts nothing, and logs why, when a run holds a browser lock as it checks, or while a launch is already under way. A run that starts after that check, before the spawn, can still get the hand-off, which #636 already allows for **Start Chrome**: an `--app` window, never an attach. `serve --reload` has no server to watch, so it doesn't start Chrome at startup. With the login item on, this starts Chrome at login.
- **Whether it's running.** `GET /linkedin/browser/health` (`chrome_running`, `chrome_pid`) and the posture report's `dedicated chrome profile` row read the live pid in the profile's `SingletonLock`, with a signal-0 check. They never connect to the port, so the row shows with `--no-probe`. A stale lock whose pid was reused reads as running, which still fails safe: startup submits the launch, no port answers, and the launcher refuses `profile_without_port` without spawning.
- **The button** is disabled while the health read says a run holds the browser, and while a start is in flight. That's a convenience, not a guarantee: a run started from a terminal doesn't reach `serve`'s event bus, so the read can be stale. The launcher's own checks still apply, and a press during a run is a hand-off at most, which #636 allows.

### Why an `--app` window

An app window has no tab strip. A run's tab never opens among the UI's tabs, and the UI's window never switches to another tab. A run that raises its own window (#632) can still cover the UI's window on screen. Links the UI opens in a new tab, such as the Gmail wizard's Console links, open in a normal window of the same Chrome. Not verified live: whether Chrome ever places a run's `background: true` tab into an app window. #632 checks this.

### No "open in netkeep's Chrome" hint

If you open the UI by hand in another browser, it works the same. It shows no hint. The page can't see its own window's debugging state, so a hint would need posture to list targets through the port and compare origins, and opening the UI elsewhere puts nothing at risk. #549's Chrome-required banner still applies to browsers that aren't Chrome. The old rule that a UI tab in netkeep's Chrome is a posture warning is dropped: that tab is now expected.

## The safety scanner and the text that changes on acceptance

`tests/test_browser_safety.py` enforces ADR 0002's no-launch rule. It bans Playwright's launch calls, the `subprocess`, `pty` and `webbrowser` modules, and every process-spawning call (`create_subprocess_exec`, `Popen`, `posix_spawn`, and the rest) anywhere in the package. The launcher breaks that ban, so on acceptance it gets one exception:

- One module, and one function in it, may spawn a process. Nothing else in the package may, including the rest of that module.
- The function builds the launcher's one argument list from config. Tests pin it to the lines netkeep prints, plus `--app=<the UI's URL>` and the first-run LinkedIn URL.
- Playwright's launch calls stay banned everywhere, with no exception.
- **Where it lives:** beside `worker.py` (for example `netkeep/chrome_spawn.py`), outside `web/`, `linkedin/`, `crm/` and `services/`, and importing nothing from `linkedin/`. Only `netkeep/cli.py` (`netkeep open`, and `browser launch --start` if it's added) and `netkeep/worker.py` (`serve`'s wiring) import it. A test pins that list of importers, as `BROWSER_CALLERS` does for the provider.
- **How a route reaches it:** the way the runs API reaches the worker. `serve` puts the spawner on `app.state` behind a Protocol in `services/`, as it does with `services.runs.RunExecutor`. The route submits the spawn to the task runner and returns at once. With no spawner on `app.state`, the route answers 503, as `_executor` does. A route never imports the module and never spawns inside a handler: the checks before a spawn can take seconds, and keeping process creation out of `web/` keeps the scanner's exception to one module.
