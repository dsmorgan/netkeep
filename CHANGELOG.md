## [0.1.0] - 2026-10-20

### Added

- Python project tooling: `pyproject.toml`, `uv.lock`, ruff, mypy, pytest, towncrier changelog fragments, and a `Makefile`. ([#1](https://github.com/dsmorgan/netkeep/issues/1))
- TOML configuration (`config.toml`, resolved from `--config`, `$NETKEEP_CONFIG`, the working directory, then the data directory), per-platform data directory resolution, `NETKEEP_LOG_LEVEL` logging, and `netkeep config show`. ([#2](https://github.com/dsmorgan/netkeep/issues/2))
- Database core: a SQLite engine with WAL and foreign keys on (`NETKEEP_DATABASE_URL` overrides the location), `session_scope()`, the `UTCDateTime` column type, Alembic wired to the models with the first migration (`users`, `settings_kv`), a migration diff test that also runs on PostgreSQL when `NETKEEP_TEST_DATABASE_URL` is set, and `netkeep db upgrade|current|revision`. `db upgrade` creates the local user on first start. ([#3](https://github.com/dsmorgan/netkeep/issues/3))
- FastAPI application factory: `netkeep serve` runs the API under `/api/v1` (`health`, `me`, the `events` SSE stream, and a `tasks/ping` diagnostic showing that routes enqueue work and answer `202`), migrates the database and creates the local user at startup, refuses state-changing requests that lack `X-Netkeep-Client: 1` or come from another origin, discovers API modules automatically, and serves the built frontend. `netkeep openapi export` writes the schema that `make gen-client` turns into the TypeScript client. ([#4](https://github.com/dsmorgan/netkeep/issues/4))
- `netkeep backup` (also `backup create`) snapshots the SQLite database with `VACUUM INTO` to `<data_dir>/backups/netkeep-<UTC timestamp>.sqlite3` and keeps the newest `[backup] keep` files (14 by default); `netkeep backup list` shows what is there with size and age. `netkeep --help` now describes every command group. ([#5](https://github.com/dsmorgan/netkeep/issues/5))
- Frontend shell: Vite, React 19, TanStack Router and Query, Tailwind CSS, and shadcn/ui, with the sidebar navigation from the spec, a dashboard that shows backend health and the current user, an SSE connection indicator, and a TypeScript API client generated from the OpenAPI schema (`pnpm gen`). ([#6](https://github.com/dsmorgan/netkeep/issues/6))
- GitHub Actions CI on pull requests and pushes to `main`: ruff, mypy, and pytest with the migration tests also run against PostgreSQL 16; frontend eslint, `tsc`, vitest, build, and prettier; and a check that the committed TypeScript client matches the backend's OpenAPI schema (`make gen-client` fixes it). Dependabot keeps the workflow's actions current. ([#7](https://github.com/dsmorgan/netkeep/issues/7))
- User scoping (ADR 0005): `netkeep.scoping` provides `scoped()`, `scoped_update()`, `scoped_delete()`, `get_scoped()`, and the explicit `unscoped()` escape hatch for queries against user-owned tables, plus a runtime guard, installed on the app's session factory and the test fixtures, that raises `UnscopedQueryError` for any select, update, or delete touching a user-owned table without the helper, and for a new user-owned row with no `user_id`. `settings_kv` gains `get_setting`, `set_setting`, and `delete_setting`. The test suite gains the two-user isolation harness (`tests/isolation/`), which discovers every list endpoint in the OpenAPI schema and fails when one is not registered. `set_setting` is a single `INSERT ... ON CONFLICT DO UPDATE` on SQLite and PostgreSQL, and SQLite connections now wait up to five seconds for a busy database instead of failing at once. ([#9](https://github.com/dsmorgan/netkeep/issues/9))
- Contact models and their migration (`0002`): `contacts` with LinkedIn identity, triage, do-not-contact, removal and enrichment counters, notes, and archive fields, plus the child tables `contact_emails`, `contact_phones`, `contact_links`, `contact_positions`, `contact_snapshots`, `contact_aliases`, and `interactions`, every one user-owned with provenance (`source`, `observed_at`) and a database-level cascade from its contact. Uniqueness is per user (`li_urn`, `li_public_id`, alias slugs, an address per contact); emails and slugs are stored lowercase; `preferred_name` starts as `first_name`. Provenance is per field: `contacts.field_sources` records which source last wrote each LinkedIn field, and `netkeep.crm.provenance` holds the precedence rule (`sync` over `archive` over `csv` over `manual`; `manual` always wins for the fields a person owns). `contacts.last_contacted_at` is a denormalized copy of the newest outbound interaction's time, kept current by whatever writes outbound interactions, so filters and sorts on it never scan the timeline. Sessions that may write now start SQLite transactions with `BEGIN IMMEDIATE` (`session_scope(write=True)`, and every request whose method is not `GET`, `HEAD`, or `OPTIONS`), so a read-then-write waits for a concurrent writer instead of failing with "database is locked". ([#10](https://github.com/dsmorgan/netkeep/issues/10))
- Identity resolution and merge (`netkeep.crm.identity`, spec 8.2). Importers and the sync hand each row to `resolve()` as an `IncomingContact` (emails and slugs lowercased, the slug derived from a profile URL, never from a URN) and get back `Matched`, `Candidate`, or `New`: a URN match, then a public-id match (current slug or a recorded alias, which also learns the incoming URN), then any email, then first name, last name, and company together, which is only ever a candidate for review. Two contacts sharing an address, or a slug whose contact carries a different URN, are candidates too. `apply()` creates or updates the contact under the field-level precedence rule, records the source of every field it writes, keeps an old vanity slug as an alias, writes a `contact_snapshot` when a job field changes, and upserts emails, phones, links, and positions by natural key so a re-import never duplicates them. `merge()` folds one contact into another: children move and deduplicate, empty fields fill from the loser with its recorded source, the loser's slug becomes an alias, `met` keeps the more decided value, `do_not_contact` sticks, notes join, and the loser records `merged_into_id`, so it resolves to its survivor from then on. `resolve()`, `apply()`, and `merge()` refuse a session that is not a writer, and `apply()` checks everything before its first write, so a row it rejects leaves the contact untouched. `netkeep.crm.provenance.set_manual_field()` is the path for a person's own edits: it writes unconditionally and records `manual`, which a later sync may overwrite for LinkedIn fields by design. ([#11](https://github.com/dsmorgan/netkeep/issues/11))
- Import a LinkedIn data archive (`netkeep.crm.archive`, spec 9.2 and 10.5). Point it at the export zip, at a directory it was unpacked into, or at one of its CSVs, and `Connections.csv` becomes contacts with provenance `archive`, while `messages.csv` and `Invitations.csv` become `li_in` and `li_out` interactions for the timeline and for triage evidence. Tables are recognized by their header rather than their file name, so the preamble that opens `Connections.csv` is skipped however long it is and however much LinkedIn changes it, and an export with no preamble reads the same way. An email address is written only for the few rows that carry one. Most message rows name no profile URL, so conversations are grouped by their id and attributed whole from any row inside them that does; group threads and conversations nobody signed are reported rather than guessed at, and so are dates in no recognizable form. Re-importing the same archive adds nothing, and a field edited by hand keeps the edit while the archive's own value stays available to revert to. ([#12](https://github.com/dsmorgan/netkeep/issues/12))
- Generic CSV importer with mapping, review, and rollback (`netkeep.crm.importer`, `netkeep.crm.import_runs`, `/api/v1/imports`, spec 10.5). Send a CSV and the importer finds its header (the LinkedIn archive's "Notes:" preamble is skipped, header cells are trimmed, a repeated or empty column still gets a key), matches columns to fields by header name through one of the built-in presets — `linkedin-archive`, `linkedhelper`, `nine-column`, each matching a normalized header so `First Name`, `first_name`, and `FIRSTNAME` are one column — and saves any mapping you settle on as a named preset of your own. A draft run stores every row as it was read and resolves the whole file, so the counts are the file's, not a sample's; a preview shows the first twenty resolutions with, per row, whether it is an existing contact, a candidate waiting for your decision, or a new contact, which fields would change, and which are refused because a more authoritative source wrote them — a manual edit above all, which no import overwrites (spec 10.5). Candidates take a `merge_into` or `create_new` decision, and a commit applies the run in one transaction, so the file lands whole or not at all. A row repeated inside the file lands on one contact; a malformed address, an undialable phone number, an unreadable date, or a URL that is not a LinkedIn profile is dropped with its reason on the row while the rest of that row still imports. New `import_runs` and `import_rows` tables record the raw cells, the resolution, the decision, and — this is what makes the undo honest — the value each field held *before* the import, alongside the source and synced-value entries it replaced and the ids of the child rows it added. `POST /imports/{id}/rollback` therefore removes only what that run created: a contact the run created is deleted, a contact it merely enriched keeps the values it had before, a contact the run never touched is left alone, and a field something changed after the import keeps that later value *and its provenance*, so an edit that outlives a rollback is still refused by the next import. A run whose created contacts a merge has since drawn in is refused rather than partly undone, because deleting one of those would take rows the run never created. ([#13](https://github.com/dsmorgan/netkeep/issues/13))
- Contacts API: list with a filter tree, sort, pagination, and column selection (`POST /api/v1/contacts/query`); quick search; one contact with its emails, phones, links, positions, and interleaved timeline; hand edits that stick under field provenance, with a revert to the last synced value; emails, phones, and links; merge; soft archive and unarchive. Bulk actions apply to a filter behind a count confirmation token: ask `POST /api/v1/contacts/bulk/count` for the count, send its signed five-minute token back with the action, and a selection that has moved -- or a value the person did not confirm -- is refused rather than applied to rows nobody saw. ([#14](https://github.com/dsmorgan/netkeep/issues/14))
- The filter language (spec 10.4): `netkeep.crm.filters` defines the JSON filter tree as Pydantic models (`and`/`or`/`not`; `eq`, `neq`, `contains`, `starts_with`, `is_empty`, `gt`, `gte`, `lt`, `lte`, `between` over an allowlist of contact columns; `has_email`, `has_phone`, `has_li_url`, `has_position`, `email_contains`; `last_contacted`, `connected_within_days`, `changed_jobs_within_days`; and placeholders for `tag_any`/`tag_all`/`tag_none`, `list_member`, `enrolled_in`, `replied_in` that parse now and compile once their tables exist) and compiles it to scoped SQLAlchemy statements (`compile_filter`, `compile_count`, `compile_update`) with `apply_sort`, `paginate`, and a `describe` reading for list headers. Every leaf is two-valued, so `not` is an exact complement; string comparisons are case-insensitive with `%` and `_` matched literally; merged-away contacts never appear and archived ones need `include_archived`. Invalid trees raise one `FilterError` with a JSON path per problem. The tree's JSON schema is snapshotted at `tests/snapshots/filter_schema.json` for the frontend builder; regenerate it with `UPDATE_SNAPSHOTS=1 .venv/bin/python -m pytest tests/test_filters.py`. ([#15](https://github.com/dsmorgan/netkeep/issues/15))
- Tags and auto-tag rules (spec 8.3, 10.3). Migration `0004` adds `tags` (a name unique per user without regard to case, a color, and a kind: `manual`, `auto`, `llm`), `contact_tags` (an assignment with its source, `manual`, `rule`, or `llm`, and the rule it came from), `contact_tag_suppressions` (an automatic tag the user removed, so no rule re-adds it), and `autotag_rules` (a case-insensitive regular expression over the title, headline, or company that feeds one tag, in a user-set order). `netkeep.crm.tags` creates, renames, and deletes tags, tags and untags contacts (a manual tag takes over an automatic one and clears its suppression; removing an automatic tag writes one), manages rules with the pattern validated at save time (a pattern is refused when an unbounded repeat contains another one, as in `(a+)+`, the shape behind exponential backtracking, or when its counted repeats multiply out past 1000, as in `(?:(?:a{100}){100}){100}`, which `regex` expands at compile time into gigabytes), previews what a pattern would match without writing, and runs the rules: every enabled rule is evaluated in Python over the live contacts in batches, a matched tag is added as a `rule` assignment unless suppressed, a `rule` assignment no enabled rule matches any more is removed, and `manual` and `llm` assignments are never touched. A default set of 13 tags with a title and a headline rule each (c-suite, vp, director, founder, investor, recruiter, engineering, product, design, sales, marketing, consultant, academic) is seeded once per user at first start and recorded in `settings_kv` under `tags.defaults_seeded`, so a default the user deletes stays deleted. The filter language's `tag_any`, `tag_all`, and `tag_none` now compile (names matched without regard to case). API: `GET/POST /api/v1/tags`, `PATCH/DELETE /api/v1/tags/{id}`, `POST /api/v1/contacts/{id}/tags`, `DELETE /api/v1/contacts/{id}/tags/{tag_id}`, `GET/POST /api/v1/autotag-rules`, `PATCH/DELETE /api/v1/autotag-rules/{id}`, and `POST /api/v1/autotag-rules/reorder|run|preview` and `/{id}/run`. CLI: `netkeep tags list` and `netkeep tags run-rules`. Every search runs with a 50 ms timeout, so a pattern that slips past the static check cannot hold the SQLite write lock: a search that times out adds no tag and removes none either, so a loaded machine cannot strip tags a quiet one keeps; it is logged with the rule and the contact, and is reported as `timeouts` by the run and preview endpoints and by `netkeep tags run-rules`. After 20 timeouts a rule is skipped for the rest of the run, which bounds what one slow pattern can cost no matter how large the address book is. ([#16](https://github.com/dsmorgan/netkeep/issues/16))
- Lists and saved table views (spec 10.1, 10.4). Migration `0006` adds `lists` (a name unique per user, a `kind` of `static` or `smart`, and a filter tree for a smart list, refused at write time unless it is valid and compiles), `list_members` (explicit membership with an `added_at`, for a static list only), and `saved_views` (a named column set, sort, and optional filter for the contacts table to restore). `netkeep.crm.lists` creates, renames, and deletes lists; adds and removes a static list's members; and answers a page of any list's members and its count, live: a smart list is never materialized, so its members are always exactly what `netkeep.crm.filters.compile_filter` returns for its stored filter right now. "Validated" (`met = "met"`, architecture.md section 3, workflow step 1.3) ships as a built-in smart list, seeded once per user like the default auto-tag rules, recorded in `settings_kv` under `lists.validated_seeded` so a copy the user deletes or renames stays gone. API: `GET/POST /api/v1/lists`, `PATCH/DELETE /api/v1/lists/{id}`, `GET/POST /api/v1/lists/{id}/members`, `DELETE /api/v1/lists/{id}/members/{contact_id}`, and `GET/POST /api/v1/views`, `PATCH/DELETE /api/v1/views/{id}`. CLI: `netkeep lists list` and `netkeep lists views`. ([#17](https://github.com/dsmorgan/netkeep/issues/17))
- Triage (`netkeep.crm.triage`, spec 10.2): the queue of untriaged contacts, one at a time, with its evidence in the same response. `GET /api/v1/triage/next` returns a card — the contact, its LinkedIn message history with counts and the newest few, the interaction and job-snapshot timeline, the companies it shares with the rest of the address book, its notes and tags — plus the card after it and the progress counters, so a keyboard run never waits for an evidence round trip. `POST /api/v1/triage/decisions` records `met`, `not_met`, or `skip` and returns the next card with the decision, which makes a run of fifty contacts fifty-one requests and a fixed number of queries per contact whatever history each one carries. `POST /api/v1/triage/undo` restores the previous state exactly, not merely "untriaged": every action writes a `triage_decisions` row (migration `0007`) holding the fields it changed as they were and as it left them, so undo puts back the earlier `met` with its original `triaged_at`, walks back one decision at a time when a contact was decided twice, reaches the decision before once one is spent, and returns the contact to its place in the queue, which is ordered by id and so never depends on a decision. Undo refuses with `409` rather than half-doing the job: when the contact no longer holds what the decision left it holding, so an edit that arrived in between is never overwritten; and when the contact has left the queue since, because neither archiving nor merging touches a recorded field, and restoring a merged-away contact would clear the decision on a row nobody reads while the survivor, which `merge` copied `met` and `triaged_at` onto, quietly kept it. `force` restores anyway and names what it overrode, and a contact named there may be restored without being back in the queue. `PUT /api/v1/triage/contacts/{id}/preferred-name` is the `p` key, written through `set_manual_field` so no later sync, archive, or CSV import overwrites it, and undoable like any decision. `GET /api/v1/triage/suggestions` offers "mark everyone with message history as met" as a preview with a count and nothing else; `POST /api/v1/triage/suggestions/{key}/apply` applies it as one batch that a single undo takes back contact by contact to where each one was, and refuses with `409` when the set has moved on since the count the banner showed. Message bodies and notes are returned exactly as they were stored, HTML and all (#75): the API escapes nothing, so whatever renders `summary` or `notes` must, and a test pins that contract. ([#18](https://github.com/dsmorgan/netkeep/issues/18))
- Interactions and notes (`netkeep.crm.interactions`, spec 8.1 and 10.1): `POST`, `PATCH`, and `DELETE` on a contact's interactions, a paged `GET /contacts/{id}/interactions`, `GET /contacts/{id}/timeline` interleaving interactions and job snapshots newest first behind a `before` cursor, and `PUT /contacts/{id}/notes` for Markdown notes. Outbound kinds (`email_out`, `li_out`, `call`, `meeting`) keep `contacts.last_contacted_at` at the newest outbound time; editing or deleting one recomputes it from the rows that remain, and `recompute_last_contacted()` repairs the column for every contact in one statement. Another user's contact answers `404`. The isolation harness now runs list endpoints whose path carries a parameter, formatting it per user through `ListEndpoint.path_params`. ([#19](https://github.com/dsmorgan/netkeep/issues/19))
- Exporters (`netkeep.crm.exports`, spec 10.6): `GET /api/v1/exports` streams contacts as CSV, JSON, or vCard 4.0, respecting the same filter and sort the contacts table and smart lists use. Four presets: `nine-column` (with a `headerless` CSV variant), the eight columns of Appendix A in order, whose CSV form round-trips through `netkeep`'s own nine-column importer unchanged; `linkedin-archive`, the columns of LinkedIn's own `Connections.csv`; `full`, every user-facing field including children (emails, phones, links, positions, tags); and `campaign-audience`, the campaign engine's merge fields plus the recipient email, which never includes a `do_not_contact` person. Every preset strips database ids, foreign keys, and sync-internal bookkeeping columns; `nine-column` and `linkedin-archive` also drop a row with nothing identifying a person (no LinkedIn URL, no name, no email, no phone) and a phone number with no digits, since the importer would refuse both anyway. Rows are fetched in bounded batches and written by a generator, so a large export never sits in memory as a whole file or result set, and the request never takes the SQLite write lock, since an export is a read. ([#20](https://github.com/dsmorgan/netkeep/issues/20))
- Contacts table and detail page (spec 10.1, 14.3). `/contacts` is a dense table whose whole state — the filter, the sort, the page — lives in the URL, so a view is a link you can paste and the back button walks your filters. Free text, company, met state, tags, do-not-contact, and archived compile to the filter tree `POST /contacts/query` takes, so filtering, sorting, and paging all happen on the server; the filter box is debounced and local to itself, so typing re-renders no rows and asks the server once. The column picker offers every scalar column the API can return and is remembered per browser, and a query asks only for the columns on screen, so hiding a column stops it crossing the wire. Saved views are the ones under `/views`: saving one stores the columns, sort, and filter under a name and applies it; applying one reads its filter back into the filter bar where the bar can say it, and uses the stored tree verbatim where it cannot. Row actions cover spec 10.1's list in full — tag, add to list, set met, set do-not-contact, archive, open on LinkedIn, open in Gmail. Adding to a list offers your static lists and puts the contact on one through `POST /lists/{id}/members`; a smart list is shown unavailable, because its membership is its filter and the API refuses members for one. Pinning for enrichment is the one action still shown unavailable with a reason rather than as a click that fails: `/linkedin/pins` does not exist yet. Bulk actions go through the confirmation flow: the dialog settles the whole sentence (including a do-not-contact reason, which the token binds), asks `POST /contacts/bulk/count` for the count, shows the server's own reading of the selection, and sends the token back; a count that moved, or a confirmation that expired, is explained in those words, says that nothing was changed, and offers to count again. `/contacts/:id` shows the fields, children, tags, timeline, and snapshots. A LinkedIn field edited by hand is marked a manual override and says what the sync last reported; reverting is a button next to it, and a field no automated source ever reported shows that button disabled with the reason instead of failing after the click. A merged-away contact is handled the way the API defines it: following its id says you were brought to the survivor, and a write that answers `409 merged` becomes a link to the contact to make the change on. A page longer than sixty rows renders a window rather than every row, sized to the viewport plus an overscan on each side; `src/test/contacts-performance.test.tsx` asserts that window exactly at ten thousand rows and after a scroll, that selecting one row re-renders one row, and that five keystrokes a half-debounce apart reach the server as one query and re-render no rows at all. New: `GET /api/v1/contacts/{id}/tags` lists a contact's tags, which the detail screen needs and nothing exposed before. ([#21](https://github.com/dsmorgan/netkeep/issues/21))
- The import wizard at `/imports` (spec 10.5): choose a CSV, map its columns from a detected preset or by hand, preview the first twenty rows resolved against your contacts, decide each candidate, and commit. The preview names the fields provenance will refuse — a value your own edit outranks is the one thing you cannot find out after committing — and the cells the importer dropped on rows that still land, such as a LinkedIn URN that is not a `urn:li:…`. Commit stays out of reach while a candidate has no decision, rather than answering 409 after the click; undecided candidates can be skipped deliberately instead. `/imports/runs` lists every run with its counts and status, and a run's own page rolls it back after spelling out what that deletes, what it puts back, and that a merge since the import refuses the rollback whole. A draft that was read but never committed can be finished from there without choosing the file again.

  The wizard reads the file's bytes and works out its encoding rather than assuming UTF-8 (issue #79). A byte-order mark settles it, UTF-16 without one is recognised by its zero bytes, valid UTF-8 is UTF-8, and anything else is read as Windows-1252 — the encoding Excel and older Windows CRMs write. The encoding used is named on the mapping screen with the reason for it and can be overridden there, so an export full of accented names no longer imports silently as `Ã‰lodie`.

  `POST /imports/inspect` no longer refuses a file whose headers no preset recognizes. It writes nothing and exists to show a file's columns, so it returns them with an empty mapping and leaves the requirement that an import map *something* to `POST /imports`, which is the call that writes. Before this, any CSV from anything but LinkedIn answered 422 on upload and the screen that could have mapped it by hand was unreachable.

  A run records the preset it was read with only when nothing edited what that preset produced. Editing one column used to leave the run filed under `linkedin-archive` with a mapping that was no longer the linkedin-archive mapping, which every screen reading `preset` then repeated. ([#22](https://github.com/dsmorgan/netkeep/issues/22))
- The triage screen (`/triage`, spec 10.2): one contact at a time with its evidence, the keyboard map, progress, the skipped-queue filter, and the bulk suggestion banner. `m` met, `n` not met, `s` skip, `u` undo, `t` tag, `p` edit the preferred name, `→` next without deciding, and `?` for a help overlay that lists all of them; the keys are handled on the window, so they work from a cold page with focus nowhere in particular, and they stand aside for a modifier, for an already-handled event, for anything typed into a field, and for an auto-repeat, because a judgement about a person is not something you hold a key down for. The `p` editor and the `t` picker belong to the contact they were opened for and close themselves when the card moves on, so a name typed for one person can never be submitted against the next. A write that does not land names its contact in a banner that the next keystroke does not erase and that `u` does not offer to take back — and an undo pressed underneath a decision still in flight is dropped rather than reaching past it to the one before, which would otherwise revert a contact silently, since both sit behind the frontier. Two cards are held at a time and the decision *is* the fetch — `POST /triage/decisions` returns the card after the one now on screen — so a run costs one request per contact and a keystroke never waits for the network; `→` moves on with a `GET` that writes nothing, tracking the furthest contact the server has handed over rather than deriving it from the buffer, so a mix of `m` and `→` never doubles back over somebody already passed. Undo's `409` is put to the person as a choice, worded separately for each of its three reasons — a field changed since the decision, the contact was archived, or it was merged into another — with the backend's own account of what diverged and `force` offered, never taken; a restored contact this queue would not serve — one whose state is out of the filter, or one that a force overrode an archive or a merge to recover — is reported rather than rendered as the next card, while a force over an ordinary edited field keeps the card it was already showing, and because tagging goes through the contacts API and not the triage log, the screen names what `u` will actually take back and says so when a tag has happened since. The bulk banner previews with a count, sends that count back with the apply, and treats a `409` as a preview to take again rather than an error. Message bodies, timeline summaries, and notes are rendered as text through an inert `DOMParser` transform that reads through a body the archive cut mid-tag (issue #75); `dangerouslySetInnerHTML` appears nowhere on the screen. The card is a polite atomic live region that never moves focus, so a screen reader announces each contact while the keyboard map stays live, and the evidence panel is its own landmark beside it — including the company overlap, labelled as overlap with the rest of the address book rather than a shared history the schema has no way to know, with the companies nobody else is at left out. Fifty contacts were driven through the keyboard in 210 ms against a real backend, 4.2 ms each, at exactly one request per contact; the same run against the offline fake in `frontend/src/features/triage/triage-throughput.test.tsx` takes about 750 ms, because its deliberate 15 ms delay dominates. The claim that matters is the one the fake does pin: at any pace slower than a round trip every card change is synchronous, asserted with nothing awaited between the keystroke and reading the card. ([#23](https://github.com/dsmorgan/netkeep/issues/23))
- Frontend for tags, auto-tag rules, lists, the filter builder, and exports (spec 10.3, 10.4, 10.6). `/lists` now holds three tabs — lists, tags and their rules, and saved views — and `/exports` holds a selection and a preset picker; both are built on the generated client, with no hand-written request or response type anywhere in the feature. ### Security

- CSV exports have an opt-in "Safe to open in a spreadsheet" setting (`spreadsheet_safe=true` on `GET /exports`, `--spreadsheet-safe` on `netkeep export`). It puts a `'` before any cell that starts with `=`, `+`, `-`, `@`, a tab, or a carriage return, so a profile field crafted as a formula shows as text in Excel, Sheets, or LibreOffice instead of running. The setting is off by default because it changes the file: a spreadsheet-safe CSV no longer re-imports cleanly, and `+1…` phone numbers gain a leading quote too. ([#76](https://github.com/dsmorgan/netkeep/issues/76))
- The local API now refuses any request whose `Host` does not name this machine (`127.0.0.1`, `localhost`, `::1`), which closes a DNS-rebinding path around the same-origin check. ([#175](https://github.com/dsmorgan/netkeep/issues/175))
- The access log redacts the Gmail OAuth callback's query (which carries the authorization code) however the path is spelled: `/callback/?code=…`, a repeated slash, or another case used to be logged in full.
  A Gmail OAuth client secret over 300 characters is refused without echoing it back in the `422` body. ([#256](https://github.com/dsmorgan/netkeep/issues/256))
- A contact's email address must now be one plain address, like `ada@example.com`. A list, a group or a display name (`Eve <eve@example.com>`) is refused, so a campaign email goes to that one person and no one else. Imports still take such an address as they find it. ([#269](https://github.com/dsmorgan/netkeep/issues/269))
- The local API now requires a per-install key (#618, ADR 0013), so other programs on your Mac that only speak HTTP can't drive netkeep. The key lives only in the Keychain. Your browser gets a session cookie (`HttpOnly`, `SameSite=Strict`) instead of the key: the first browser to load the UI after the upgrade connects itself, and another browser connects through the link `netkeep open` prints. Health, the Gmail OAuth callback and the connect endpoints stay open.

  When the Keychain refuses the key, netkeep still starts on a key kept in memory, and says so: the UI shows a banner, and the connect page and `netkeep open` explain that restarting reconnects the first browser. The session cookie is renewed on every UI load, so a browser in use never has to reconnect. ([#618](https://github.com/dsmorgan/netkeep/issues/618))
- The preflight cookie read now asks Chrome itself (CDP `Network.getCookies` with LinkedIn's URL) for only LinkedIn's cookies, so no other site's cookie, such as Google's once Gmail is linked, leaves the browser for netkeep (ADR 0012). ([#633](https://github.com/dsmorgan/netkeep/issues/633))
- While a run waits for the tab it opened, it now reads only a new tab still on `about:blank` and claims it by target id, so a UI or Google tab you open at that moment gets no session. `message-check --bubble` never reads the run's own tab. A test pins every read of the browser's tabs in the package to the run's own tab or LinkedIn's origin, and every close and bring-forward to the run's own tab. ([#634](https://github.com/dsmorgan/netkeep/issues/634))
